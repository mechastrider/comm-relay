# Готовность к релизу после v0.5.0

Проверка от 2026-11-04. База сравнения: локальный тег `v0.5.0` от 2026-08-25 → `c154148` (85 коммитов, включая merge-коммиты). Проверены история Git, текущий код и канонические спецификации, CHANGELOG, оба README, активные изменения OpenSpec и release/CI workflow. Публикация релиза и создание тега не выполнялись; Дополнительно проверен GitHub Actions run 41828117277 на том же коммите: Go test (включая race) и lint прошли, browser regression завершилась 108/109. Реальные desktop/OBS-сборки этой проверкой не подтверждены.

## Вывод

Документация подготовлена к большому функциональному релизу. Первичная проверка выявила гонку ожидания сохранения Studio и падение сетевого процесса WebKit в CI. В ходе подготовки исправлены ожидания двух Studio-тестов и обновлён Playwright до 1.64.1 с исправленным WebKit. Результаты повторной проверки приведены ниже; перед выпуском остаются проверка обновления данных и готовых desktop-архивов. По объёму это следующий minor-релиз, а не patch; `0.6.0` использован только как кандидат в проверке CHANGELOG. Окончательный номер и дата не назначены.

Главное изменение для пользователя — переход от мультичата с рейтингом к интерактивному эфиру: награды и XP, прогрессия, команды и социальные действия зрителей, собственные баннеры, приветствия, задачи и итоги. Именно это стоит вынести в анонс; список внутренних переделок админки пользователю не нужен.

## Найденная нестабильность браузерной регрессии

Полный Chromium-прогон: **80 passed, 1 failed**. Сценарий `viewer visual Studio switches default on and persist independently` в [viewer-visual-status.spec.ts](../../web/e2e/viewer-visual-status.spec.ts) после выключения обойм, публикации и перезагрузки получил включённый переключатель. Три отдельных повторения с одним worker прошли: **3/3**. Потеря настройки при завершённом сохранении этим не подтверждена.

Trace первого прогона не содержит POST сохранения до reload. Тест после клика ждёт только `toBeDisabled()`, но [StudioFrame](../../web/admin/src/features/studio/StudioFrame.tsx) отключает кнопку и при `busy`, и при отсутствии изменений. [Studio](../../web/admin/src/features/studio/Studio.tsx) устанавливает busy до асинхронного чтения свежего config и его записи. Следовательно, ожидание может завершиться в начале операции и позволить reload отменить её. Это обоснованная причина нестабильности; для окончательного подтверждения нужно изменить ожидание и повторить полный прогон.

Исправление: ожидать успешный `POST /api/config/update`, завершение `aria-busy` и опубликованное состояние, затем делать reload и проверять API/переключатель. На этапе диагностики код не менялся. Затем оба Studio-теста с таким ожиданием исправлены: они ждут успешный ответ записи, `aria-busy=false` и отключённую кнопку до чтения config или reload. Продуктовый код не менялся. Первичное локальное свидетельство — Playwright trace и screenshot сценария в `test-results` (генерируемые артефакты не входят в Git).

## Дополнение: падение WebKit в GitHub Actions

Источник: [Browser regression, run 41828117277](https://github.com/mechastrider/comm-relay/actions/runs/41828117277/job/126567990949), коммит `c15414844cc7ba908471dad14d247c9c4c56bbed`, 2026-11-04. Проверены лог задания и загруженный Playwright trace.

- **108/109 passed**: все 81 Chromium-сценарий и 27 из 28 WebKit-сценариев. Упал только `recap browser PNG download and native bridge cancellation use the shared exporter` в [resilience.spec.ts](../../web/e2e/resilience.spec.ts), ожидание download на строке 104.
- Примерно через 2,65 секунды после клика скачивания trace сообщает: `WebSocket network error: Network process crashed`. Затем три запроса CSS для генерации PNG завершаются `WebKit encountered an internal error`. До этого создание снимка через POST вернуло 200.
- Тест не получает download и достигает общего таймаута 45 секунд. Последующее `Target page, context or browser has been closed` — сообщение ожидающего download при закрытии контекста теста; само по себе оно не доказывает падение приложения CommRelay.
- Это отдельная проблема от локальной гонки Studio. На этапе чтения trace причина падения сетевого процесса WebKit ещё не была установлена: trace доказывает сбой браузерного процесса, но не позволяет выбрать между дефектом движка, окружением CI и вызвавшим его сценарием приложения. Автоматическое увеличение таймаута или пропуск WebKit не устранят установленную причину отсутствия download.
- Локальный повтор был предпринят трижды, но WebKit не запустился из-за отсутствия `libgstcodecparsers-1.0.so.0`; это ограничение местного окружения, а не повторение CI-сбоя.

Продолжение расследования: после подключения распакованных системных библиотек изолированный сценарий на прежнем WebKit прошёл 3/3; начальный расширенный прогон остановлен после 24 успешных сценариев для обновления зависимости. Обнаружена [upstream-ошибка Playwright #42803](https://github.com/microsoft/playwright/issues/42803): сборка WebKit 2359 из Playwright 1.63.0 содержит libsoup 3.6.5 с use-after-free при отмене запросов. Версия библиотеки подтверждена непосредственно в установленном бинарнике. Ошибка совпадает с наблюдаемым падением NetworkProcess; core dump CI для окончательного сопоставления стека отсутствует. Исправленная библиотека включена upstream в Playwright 1.64.

В этой ветке Playwright обновлён до 1.64.1 вместе с lockfile. В новой сборке WebKit 2370 непосредственно проверена версия libsoup: 3.6.6. Поведение приложения, retries, таймауты и набор проверяемых движков не ослаблены. Дополнительная техническая запись в CHANGELOG не добавляется: это исправление тестового окружения.

В этом же удалённом запуске задания [test](https://github.com/mechastrider/comm-relay/actions/runs/41828117277/job/126567991331) и [lint](https://github.com/mechastrider/comm-relay/actions/runs/41828117277/job/126567991360) успешны. По CI workflow это подтверждает `go test ./... -race -count=1` на исходном коммите; незавершённый локальный race-прогон не означает дефект backend.

## Что полезно поправить в выпуске

1. **Согласовать содержимое CHANGELOG в архиве и на GitHub Release.** Сейчас `build` копирует README/CHANGELOG в архивы, а `publish` позже переводит Unreleased в версию на `main`. Вложенный CHANGELOG поэтому может отличаться от опубликованного. Подготавливать версионную копию до упаковки, не меняя опубликованную историю.
2. **Привязать release notes к коммиту кандидата.** `publish` переключается на актуальный `main`, хотя бинарники собирались на checkout события. Если main сдвинется, заметки могут описывать ещё не вошедшие в бинарник изменения. Проверить этот сценарий до запуска публикации; фиксировать источник заметок вместе с исходниками кандидата.
3. **Доставить руководство пользователю архива.** Workflow копирует только два README, CHANGELOG и LICENSE: папки `docs` внутри архива нет. Относительные ссылки на руководство, FAQ и картинку README там не работают. Добавить нужные документы с сохранением структуры либо использовать доступные онлайн-ссылки для упакованных README.
4. **Подтвердить frontend-регрессию перед тегом.** Release workflow сам запускает Go-проверки и frontend build, но не typecheck/lint/tests/Playwright. Эти проверки есть в обычном CI; выпускать только точный коммит с подтверждённым результатом либо добавить релевантные проверки в release gate. Firefox вынесен в отдельный scheduled/manual workflow — при необходимости запустить перед релизом.

Это замечания по текущему [release workflow](../../.github/workflows/release.yml), а не выполненные изменения процесса публикации.

## Подача возможностей

Рекомендуемая структура материалов уже отражена в документах: README — обзор и установка, руководство — повседневные сценарии, FAQ — сбои, CHANGELOG — различия версий. Перед выпуском полезно добавить:

- Три актуальных скриншота: эфир с наградой и прогрессией, Studio с четырьмя поверхностями, готовые итоги. Не использовать случайные личные данные зрителей.
- Короткое видео «первый интерактивный стрим»: подключение → одна награда → лайк зрителя → итоговая PNG. Оно объяснит продукт лучше длинного перечня вкладок.
- Короткий анонс с тремя результатами: отметить вклад, вовлечь зрителей, сохранить финал эфира. Ссылка на релиз и отдельная заметка о резервной копии.
- Английскую версию руководства, если англоязычные пользователи входят в аудиторию этого выпуска. Сейчас перевод полного руководства не подготовлен.

Не нужно задерживать исправления и проверку миграции ради новых функций. Обновление скриншотов и видео — материалы выпуска, а не отдельные пункты CHANGELOG.
