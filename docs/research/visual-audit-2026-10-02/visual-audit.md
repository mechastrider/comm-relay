# Визуальный аудит CommRelay

Дата: 2026-10-02. Исходный commit: `e7e22fa`. Статус: исследование и рекомендации, без реализации.

## Область и доказательства

Проверена визуальная согласованность административного интерфейса для стримера/оператора: геометрия компонентов, палитра, типографика, поверхности, группировка и переиспользование. Это не повторный UX-аудит: сценарии, доступность, производительность и корректность сохранения не оценивались заново.

Просмотрены код React/CSS, canonical `openspec/specs/admin-design-system/spec.md` и живые страницы в Chromium. Использована существующая локальная сборка frontend и сервера с отдельной тестовой БД, стандартными каталогами и выключенными платформенными коннекторами. Исходники продукта не менялись, сборка заново не выполнялась. Основной viewport 1440×900; дополнительные снимки приветствий — 1100×700 и 390×844. Это не полная проверка responsive.

Покрытие: все семь вкладок Аудитории; четыре вкладки Эфира; Студия в основном режиме и диалог подключения OBS; пять разделов Настроек; О программе. На платформах основной визуальный образец — Twitch. Зрители, история, статистика и лидерборд проверены преимущественно в пустом состоянии. Все состояния диалогов, заполненные таблицы, остальные режимы Студии, native Wails/OBS, сами overlay-темы и dock в этот аудит не входят. Их иной визуальный язык нельзя считать дефектом админки.

Доказательства: [снимки страниц](evidence/), [замеры DOM/CSS](evidence/measurements.json). По просьбе владельца PNG этого аудита исключены из Git и доступны только локально; JSON замеров и текст отчёта можно хранить в репозитории. Замеры включают элементы с ненулевым bounding box, в том числе скрытые семантические заголовки и фон открытого диалога; они не являются строгим списком видимых элементов. В частности, 24px заголовки Live/Audience из JSON не используются как доказательство визуального разнобоя. Запись `settings/general` — резервный переход на Platforms, не отдельная страница. `studio.png` показывает автоматически открывшееся подключение OBS; `studio-main.png` — страницу после закрытия диалога. Дополнительные снимки сделаны после основной серии замеров.

## Вывод

У интерфейса есть узнаваемая основа: тёмные нейтральные поверхности, моноширинный шрифт, янтарная навигация, небольшие радиусы и физический рельеф кнопок. Новый визуальный стиль с нуля не нужен. Согласованность нарушается внутри этой основы: часть элементов управляется общими токенами, часть локальным CSS, часть стандартными стилями браузера. Особенно заметны рамки приветствий, разная плотность кнопок и разный масштаб заголовков. Переиспользование CSS уже значительное, но общие React-примитивы покрывают лишь часть интерфейса. Лучший следующий шаг — закрепить единый контракт существующих компонентов и последовательно перевести на него страницы.

## Приоритетные находки

Шкала серьёзности здесь оценивает визуальную согласованность, не блокирование пользовательских задач. P1 — первая очередь выравнивания, P2 — следующая. M — средняя серьёзность, L — низкая. Трудоёмкость S — локальная правка, M — компонент и его потребители, L — сквозная миграция. Ни одна находка не объявляется блокирующим UX-дефектом.

| ID | Приоритет / серьёзность | Наблюдение | Уверенность | Работа / риск |
|---|---|---|---|---|
| VIS-01 | P1 / M | Браузерные рамки приветствий и отсутствие общих секций соседних редакторов | Код + рендер + computed CSS | M / средний |
| VIS-02 | P1 / M | Размер кнопки зависит от страницы и каскада, типографика тоже меняется | Код + замеры | M / средний |
| VIS-03 | P1 / M | Одинаковые действия получают разные цветовые роли | Код + рендер | S–M / низкий |
| VIS-04 | P1 / M | Поля и подписи имеют конкурирующие базовые определения | Код + рендер | M / средний |
| VIS-05 | P2 / M | Заголовки и секции не образуют общей шкалы | Код + рендер + замеры | M / средний |
| VIS-06 | P2 / L | Chips, checkbox и range выпадают из палитры | Код + рендер, chips также computed CSS | S–M / низкий |
| VIS-07 | P2 / M | Разметка повторяется без общего владельца визуального контракта | Наблюдается в коде | L / средний |

### VIS-01. Сохранить группировку, заменить оформление секций

На «Приветствиях» блоки «Поведение», «Текст», «Медиа» имеют computed border `2px groove rgb(107, 107, 107)` и браузерные отступы `5.6px 12px 10px`. Это стандартный `fieldset`, а не выбранная карточка дизайн-системы. «Внешний вид» на той же странице имеет border 0 и padding 0. Рамки выглядят светлее и грубее тонких границ остальных панелей.

Источники: `web/admin/src/features/catalog/Fields.tsx:1264`, `:1296`, `:1351`, `:1644`; `web/admin/styles/forms.css:39`; `web/admin/styles/viewers.css:1429`. [Приветствия](evidence/audience-greetings.png), [Награды](evidence/audience-awards.png), [Команды](evidence/audience-commands.png).

В наградах и командах похожие настройки идут последовательностью полей. Оператор видит разную степень группировки близких редакторов. Предложение: общий `FormSection` с семантическим fieldset/legend, но полностью заданным оформлением: тихая поверхность, тонкая нейтральная рамка или разделитель, одинаковые внутренние отступы и заголовок. Для приветствий и наград использовать группы «Поведение/основное», «Текст», «Медиа», «Внешний вид» по смыслу. Для команд — «Команда», «Действие», «Ограничения» и условные секции баннера, когда они применимы. Не показывать пустые группы ради симметрии. Не добавлять рамку каждому полю и каждому вложенному контейнеру.

### VIS-02. Одинаковая геометрия действий, отдельная роль акцента

В токенах действительно предусмотрены две плотности: 38 и 30px. Но текущие различия этим не исчерпываются:

| Контрол | Фактическая высота на desktop |
|---|---:|
| Сохранить/Тест в приветствиях; Сохранить в каталогах | 30px |
| Новый стрим/Открыть лидерборд в Аудитории | 38px, хотя класс тоже `btn-small` |
| Обновить в Аудитории | 38px |
| Обновить в диагностике | 40px |
| Иконки управления пресетом в Студии | 30px |
| Копировать/Повтор в превью Студии | 40px |
| Обычный `.button-secondary` | CSS minimum 36px |

Источники: `tokens.css:60`, `components.css:27`, `:101`, `:108`, `:113`; `viewers.css:152`. Последнее правило `.button-secondary` переопределяет minimum 30px у `.button-secondary--small` на 36px. Размер обычного текста кнопки не задан в базе и наследуется: в снимках 16px против 11px у small. Даже «Загрузить» и «Очистить» в одной строке имеют 12 и 11px: upload реализован label, на который действует правило оформления подписей формы.

Это усиливает ощущение случайной важности: размер определяется местом и HTML-тегом. Рекомендую единый desktop action control: например, 38px высоты, один размер текста 12px, один горизонтальный padding и квадратную icon-only кнопку той же высоты. Это предлагаемое значение, а не уже утверждённый контракт. Ширина текстовых кнопок естественно зависит от надписи; одинаковая ширина всем кнопкам не нужна. На узком экране сохранить существующие увеличенные цели 44px.

Primary/secondary/danger должны отличаться цветом текста, заливкой и границей при одинаковой геометрии. Chips, выбор темы, строки списка и навигация — отдельные типы контролов: их не нужно насильно делать обычными кнопками. Компактную плотность оставлять только при явном назначении целой панели, а не выбирать произвольно для каждой кнопки.

### VIS-03. Зафиксировать цветовую роль действия

«Сохранить» в Настройках использует `btn-start`, а в Приветствиях/Командах/Наградах — нейтральную `btn-physical`. «Опубликовать» в Студии зелёная; «Анонсировать» в Контрактах — нейтральная. Разрушительные действия уже в основном выделены красным.

Источники: `web/admin/src/features/settings/Settings.tsx:322`, `web/admin/src/features/catalog/Catalog.tsx:521`, `web/admin/src/features/catalog/Greetings.tsx` (`greetings-save`); [настройки](evidence/settings-data.png), [контракты](evidence/live-contracts.png).

Оператору приходится читать надписи, чтобы отличить основной шаг от вспомогательного. Рекомендация: единые варианты `primary`, `secondary`, `danger`; сохранить зелёный для подтверждающего действия, янтарный для выбранного элемента/навигации, красный для удаления. «Тест», «Сбросить», «Закрыть» — нейтральные. Смысл поддерживать текстом/иконкой, а не одним цветом. Позицию и размер не использовать как случайный побочный эффект CSS. Несколько независимых форм могут иметь собственные primary-кнопки.

### VIS-04. Один контракт поля и подписи

`components.css:179` задаёт 38px, фон `--surface-dark` и равномерную границу; `forms.css:105` меняет те же поля внутри `.form__field` на 42px, фон `#111`, верхнюю/левую границу `#555`. В `forms.css:213` подсказки и ошибки становятся 12px вместо 11px базы, error — `#ffb8bd` вместо семантического danger. Это управляется порядком импортов `web/admin/src/styles.css`.

[Награды](evidence/audience-awards.png) смешивают компактные uppercase-подписи с крупной обычной «Картинка баннера». [Прогрессия](evidence/audience-progression.png) использует обычные подписи, а Настройки — uppercase. Разница не сообщает иной смысл поля.

Рекомендация: общие `Field`, label/hint/error и стили input/select/textarea. Один источник геометрии и палитры; feature-CSS отвечает за сетку и размещение. Высоту textarea и область загрузки оставить специализированными. Для подписей выбрать один регистр и вес; не обязательно делать весь интерфейс uppercase. Проверять также label-кнопки загрузки: нельзя позволять селектору подписи поля менять их шрифт.

### VIS-05. Общая типографическая шкала и язык поверхностей

Измеренные заголовки: редакторы каталогов — 11px/600; карточки Прогрессии — 16px/700; заголовки панелей Настроек — 13px/700 uppercase; «Состояние приложения» в диагностике и «Превью» Студии — 18.72px/700. Legend приветствий — 16px/400. Большой размер диагностики связан с h3, не охваченным правилом `.panel-heading h2`.

Источники: `viewers.css:69`, `:1178`; `forms.css:15`; `console.css:46`; `web/admin/src/features/settings/Diagnostics.tsx:73`; замеры и [диагностика](evidence/settings-diagnostics.png).

По снимкам заметны несколько способов оформления одинакового уровня: панели Настроек с отдельной полосой заголовка, карточки Прогрессии без неё, крупные голые заголовки диагностики с янтарным разделителем. Каталоги лучше согласованы между собой: единые шапки списка и редактора уже работают.

Предложение: определить роли workspace-title / panel-title / section-title / label / body / hint, отдельно от выбора h2/h3/legend. Ввести общий `PanelHeader` и правила поверхности: крупная рабочая панель, вложенная секция формы, выбранная строка. Использовать одинаковые padding/gap для одного уровня. Сохранить разные композиции страниц: трёхколоночная Студия и список-редактор не должны становиться одинаковой сеткой. Сама темнота, моноширинность и рельеф кнопок — существующее направление, а не ошибка.

### VIS-06. Убрать случайные цвета и формы малых контролов

Chips `{viewer}` имеют radius 999px, font 13.6px и прозрачный фон. Hover измерен как `rgb(59,130,246)`, синий. Причина: `viewers.css:1288` ссылается на отсутствующие `--surface-elevated`, `--bg`, `--accent`, последнее с fallback `#3b82f6`. [Снимок hover](evidence/greetings-chip-hover.png). Это выпадение из янтарной палитры; pill-форма сама по себе допустима, если её явно определить как вариант вставки переменной.

Нативный range наград голубой, громкость Настроек янтарная. Checkbox команды маленький стандартный голубой, в Прогрессии/Настройках зелёный и крупнее. Источники: `forms.css:183` и `:234`, `viewers.css:1413`; снимки команд, наград и приложения. Общие стили зависят от wrapper-классов, а не от единого контракта контрола.

Рекомендация: отдельные согласованные варианты Chip, Checkbox, Range; единые accent-color, размеры, подписи. Выбор конкретного радиуса chips — вкусовое решение, синий fallback — технически подтверждённая несогласованность. Дополнительно в `live-recap.css:23` есть отсутствующий `--primitive-radius-2`: исправить на существующий токен после проверки нужной формы.

### VIS-07. Переиспользование есть, но преимущественно через классы

Статический подсчёт вхождений строк в TSX (включая модификаторы классов), не число экземпляров на экране:

| Механизм | Вхождения / файлы |
|---|---:|
| `btn-physical` | 116 / 23 |
| `btn-small` | 80 / 19 |
| `button-secondary` | 24 / 4 |
| `form__field` | 143 / 8 |
| `<Tabs` | 3 / 3 |
| `<Dialog` | 10 / 8 |
| `<Modal` | 6 / 5 |
| Нативный `<button` | 166 / 34 |

Уже переиспользуются Tabs, Dialog/Modal, CopyButton, TemplateChips, AlertEmblem, редактор Catalog для команд/наград. Это полезная база. Отдельного общего Button/IconButton, оболочки Field и FormSection нет. Greetings повторяет часть структуры Catalog; поля трёх редакторов собраны в большом `catalog/Fields.tsx`. CSS Tabs тоже определяется в `components.css:147` и `dialogs.css:49`, что создаёт второй источник визуального решения.

Рекомендация: сначала нормализовать существующие CSS-примитивы, затем закрепить их небольшими React-компонентами. Не переносить доменную логику в универсальную огромную форму. Не создавать один компонент «на любую страницу». Владельцы правил: UI-примитив — геометрия/состояния, layout — расположение, feature — данные и условия отображения. Иначе новое имя компонента сохранит старый каскад.

## Направление выравнивания

1. Утвердить маленький визуальный контракт: высота и шрифт действий, цвет primary, 2–3 уровня заголовков/поверхностей, шаги отступов, оформление вложенной секции.
2. Сделать образцом три соседних редактора: Приветствия, Награды, Команды. Общие секции и media-поля, одинаковые шапки/кнопки; условные различия содержания сохранить.
3. Перенести тот же контракт на Прогрессию, Настройки, диагностику, toolbar Аудитории/Эфира, chrome Студии и диалоги. Стили содержимого OBS-preview не менять.
4. Удалить конкурирующие глобальные определения и локальные переопределения геометрии, проверить все потребители. Добавить компактную внутреннюю витрину компонентов/визуальные эталоны, чтобы следующие страницы не изобретали третий вариант.

Быстрые отдельные исправления: заданный стиль fieldset/legend; правильные токены chips; одинаковый акцент checkbox/range; роль кнопки сохранения. Простая замена всех `btn-small` без миграции каскада не решит проблему.

## Критерии для будущего изменения

- Одинаковые action-кнопки имеют одинаковые computed height, font-size, padding и radius в одном режиме плотности независимо от страницы и HTML-тега.
- Primary/secondary/danger отличаются оформлением, не размером. Исключения плотности перечислены явно.
- Ни один редактор не наследует случайную браузерную рамку fieldset; одинаковые группы имеют общий стиль.
- Для полей, подсказок, заголовков и состояния выбора есть один источник визуальных значений; отсутствующие CSS variables не определяют внешний вид.
- Screenshot regression: три каталога, Прогрессия, Settings, Live, Studio, диалог при 1440×900, 1100×700, 390×844; RU/EN, normal/hover/focus/disabled/busy и длинные подписи. Контролы не обрезаны, body панелей прокручивается.
- Выполнить штатные frontend typecheck/lint/unit/build/e2e, дополнить проверкой реального Wails при выпуске. Перенос стилей не меняет API, сохранение, keyboard/focus и структуру данных.

Дальнейшая реализация — отдельный OpenSpec change профиля `desktop-change`, затрагивающий admin-design-system и связанные admin contracts. Ориентировочно Tier 2.5: изменение визуального контракта нескольких поверхностей. Этот отчёт не является авторизацией реализации и не создаёт roadmap-обязательств. Новый UI-kit, смена шрифта/бренда, переделка overlay и повторный UX-аудит не требуются для устранения найденного.

## Проверки и ограничения

Для аудита использованы навигация, переключение вкладок, закрытие OBS-диалога, hover chips, снимки и computed CSS. Полный test suite и новая сборка не запускались: исходники продукта не менялись. Рендер проверен только на существующей локальной сборке Chromium; переносимость нативных контролов на Windows WebView требует проверки при реализации. Предыдущие UX-находки здесь не переоцениваются. Новых записей changelog и изменений canonical specs нет, поскольку поведение не изменялось.
