# Разбор заметок по интерфейсу и интерактивам

Статус: **материал для обсуждения**, не спецификация и не план реализации.

Источник: наблюдения во время реального стрима, переданные в виде расшифровки аудиозаметки.

Цель документа — отделить подтверждённые пробелы текущего интерфейса от уже реализованного поведения и более крупных продуктовых идей. После согласования каждый самостоятельный блок следует оформлять отдельным OpenSpec change, а не реализовывать всё одним изменением.

## Краткий вывод

В заметке смешаны три масштаба работы:

1. **Локальные улучшения интерфейса** — таблица Audience, выбранные строки каталогов, выравнивание действий и единая визуальная грамматика переключателей.
2. **Пробелы поведения во время эфира** — Live Leaderboard и Statistics в админке не следуют за новыми сообщениями автоматически; объединённый профиль в списке зрителей показывает только последнюю платформу.
3. **Развитие интерактивной системы** — связь награды с исходным сообщением, разные типы алертов, приоритеты очереди, сохранённые сообщения, переменные шаблонов и локальная медиатека.

Часть идей уже поддержана направлением [Interactive System v1](../interactive-system-v1.md): расширенный каталог наград, highlight как overlay-action, локальные изображения и звуки, Reward Library и очередь redemptions. Эта заметка уточняет операторский UX и несколько отсутствующих контрактов, но не заменяет концепт.

## 1. Audience и общая визуальная система

### Таблица зрителей

Рекомендуемое направление:

- отделить `thead` собственной поверхностью или границей, сохранив достаточный контраст текста;
- сделать Score и Messages кнопками сортировки с видимым направлением и `aria-sort`;
- сохранить текущий порядок «последняя активность» как исходный, а первый клик по числовому столбцу делать по убыванию;
- открывать/выбирать зрителя одним кликом по строке на широком экране и показывать карточку справа;
- убрать повторяющуюся колонку Actions только после появления доступной клавиатурной альтернативы: имя зрителя может быть семантической кнопкой, а Enter/Space — открывать ту же карточку;
- показывать все уникальные платформы объединённого профиля компактными SVG-значками с доступным текстовым названием и tooltip, не полагаясь только на цвет;
- выровнять New stream с другими действиями панели и не смешивать его визуально с фильтрами: это подтверждаемое горячее действие с отдельным диалогом.

Для списка платформ нужен небольшой контракт API: summary должен содержать как минимум набор уникальных platform ids. Полные логины и идентичности по-прежнему могут загружаться только для карточки.

### Выбранные команды и награды

Текущую ARIA-семантику следует сохранить, но selected должен отличаться от hover минимум двумя сигналами: например, постоянной боковой меткой и более сильным начертанием/контрастом текста. Hover остаётся временной реакцией на указатель; выбранная строка не должна становиться визуально неотличимой после ухода курсора.

### Не «одинаковые табы», а единая таксономия

Предлагаемая грамматика:

| Роль | Примеры | Визуальный паттерн |
|---|---|---|
| Основные рабочие области | Live, Audience, Studio, Settings | Боковая/нижняя навигация с иконкой и подписью |
| Равноправные разделы одной области | Messages / Leaderboard / Statistics; Viewers / Commands / Awards; разделы Settings | Один общий tab-компонент |
| Режим представления тех же данных | Essentials / All settings | Segmented control, не tab |
| Выбор редактируемой OBS-поверхности | Chat / Leaderboard / Alerts | Surface rail/list с иконкой и явным selected |

Так система останется предсказуемой, но семантически разные действия не будут искусственно выглядеть одинаково.

## 2. Live-обновление лидерборда и статистики

Нужно различать два продукта:

- OBS-лидерборд уже подписан на `leaderboard` frames и обновляется в реальном времени;
- административные Live-вкладки этих frames не используют.

Рекомендуемая модель:

1. Live → Leaderboard применяет уже существующий WebSocket snapshot для выбранного периода.
2. При повторном подключении и первом открытии остаётся HTTP snapshot, поэтому экран не зависит только от будущих событий.
3. Statistics обновляется из того же источника данных либо получает отдельный компактный summary event. Не стоит делать новый полный HTTP-запрос на каждое сообщение.
4. Скрытая вкладка может хранить последний snapshot и отрисовать его при открытии; фоновые перерисовки не нужны.
5. Ошибка одного источника оставляет предыдущие значения со статусом «обновляется/устарело», как уже требует admin design system.

Отдельно надо решить, должна ли в реальном времени обновляться вся таблица Audience. Существующий leaderboard snapshot ограничен топом и не подходит для синхронизации полного каталога зрителей.

## 3. Награда должна быть связана с исходным сообщением

Сейчас grant адресует зрителя (`platform`, `user_id`, `award_id`), но не конкретную реплику. Поэтому overlay не может надёжно понять, какую карточку подсветить, а alert — что процитировать.

Предлагаемый пользовательский результат:

```text
Reward выбран в Live/dock
        │
        ├─ чат overlay: существующая карточка получает рамку + «+25»
        │
        └─ alert: тип награды, автор, «+25» и короткая цитата сообщения
```

Рекомендации:

- award grant несёт необязательный origin исходной реплики: platform, стабильный message id при наличии и ограниченный snapshot текста из выбранной строки;
- сервер использует origin только как контекст показа, а зрителя и начисление по-прежнему определяет по проверенным `platform`, `user_id` и `award_id`;
- если карточка ещё присутствует в chat overlay, она подсвечивается на 2–3 секунды; истёкшее сообщение не возвращается в ленту искусственно;
- alert может показать короткую цитату для любого grant, начатого из строки чата, поэтому смысл награды сохраняется, даже если сообщение уже ушло вверх;
- длинный текст ограничивается по строкам/символам, а DOM строится безопасными text nodes;
- `prefers-reduced-motion` заменяет пульсирующую рамку статичным акцентом; начисление не передаётся только цветом;
- для сообщений без стабильного id Reward по-прежнему может начислять очки зрителю, но подсветка исходной карточки будет best-effort.

Открытый вопрос: надо ли хранить текст award-цитаты в журнале взаимодействий. Для мгновенного алерта достаточно transient snapshot; для будущего аудита или повторного показа потребуется явная политика хранения.

## 4. Команды и награды на одной alert-поверхности

Одна Browser Source остаётся удобнее для OBS, но два типа событий должны иметь разные роли:

- **command** — инициированное зрителем развлекательное событие: триггер, имя, изображение/аватар;
- **award** — подтверждение от оператора: название награды, `+points`, автор и цитата исходного сообщения.

Рекомендуемая диспетчеризация:

1. Видимый alert никогда не прерывается.
2. События по умолчанию идут через одну ограниченную очередь.
3. При перегрузке операторские awards не должны молча вытесняться потоком команд: сначала истекают или удаляются старые command-события.
4. Для команд нужен срок актуальности; запоздавший на десятки секунд мем обычно хуже пропуска.
5. Потерянные/просроченные события отражаются в диагностике, хотя на экран не выводятся.

Это немного сложнее строгого FIFO, зато сохраняет смысл ручной награды. Альтернатива — две отдельные OBS Browser Sources; она даёт независимую режиссуру, но усложняет настройку сцены и допускает визуальное наложение. Для ближайшей версии рекомендуется одна поверхность с разными вариантами карточки и защищённой полосой приоритета для awards.

## 5. Прозрачность и размеры alert

### Прозрачность

Не следует вводить непрозрачность всей HTML-страницы: фон Browser Source должен оставаться прозрачным. Полезнее разделить:

- прозрачность фона/chrome карточки;
- контраст текста и рамок;
- при необходимости — отдельные overrides для Chat, Leaderboard и Alerts.

Первый шаг обсуждения — проверить, решает ли задачу уже существующий `panel_opacity`, если сделать его заметнее в Studio. Если нет, предпочтителен per-surface background/chrome opacity с возможностью «использовать общее значение». Полное `opacity` контейнера нежелательно как основной контроль: вместе с рамкой оно ослабляет и текст.

### Размер alert

Текущий viewport уже занимает всю Browser Source, но контент всегда остаётся компактной карточкой. Вместо обязательного растягивания всех алертов нужен параметр layout:

- `card` — текущая компактная карточка;
- `banner` — широкая полоса, использующая доступную ширину;
- `fullscreen` — режиссируемый splash на весь источник.

Это согласуется с Reward Library, где popup и full-screen splash — разные виды интерактива. Размер Browser Source по-прежнему задаётся в OBS, а CommRelay адаптирует композицию внутри него.

## 6. Сохранённые сообщения как идеи от аудитории

Эта механика не должна незаметно превращать CommRelay в полный архив чата. Рекомендуемая граница:

- оператор явно нажимает Save/звезду в Live или dock;
- в SQLite сохраняется только выбранный snapshot: платформа, source message id при наличии, автор, текст, время сообщения и время сохранения;
- сохранение переживает перезапуск и склейку профилей;
- отдельный список «Сохранённые» позволяет удалить запись, добавить короткую заметку и вернуться к ней после стрима;
- экспорт, теги и привязка к таймкоду записи могут быть последующими расширениями.

Ключевые решения до спецификации:

- место списка: фильтр/подраздел в Live выглядит ближе к сообщениям, чем Audience;
- срок хранения и ручная очистка;
- сохранять только plain text или также безопасные fragments/preview;
- нужен ли таймкод относительно начала текущей сессии;
- что происходит при удалении исходного сообщения из оперативной истории.

## 7. Шаблоны, имя стримера и локальные медиа

### Переменные шаблонов

Текущий `{name}` означает зрителя, из-за чего seed `Hi, {name}!` визуально похож на приветствие зрителя самому себе. Более ясный словарь:

| Переменная | Значение |
|---|---|
| `{viewer}` | имя участника, вызвавшего команду или получившего награду |
| `{streamer}` | настроенное отображаемое имя стримера |
| `{points}` | начисленные очки |
| `{message}` | короткая исходная реплика, если событие связано с сообщением |

`{name}` стоит сохранить как совместимый alias `{viewer}`, чтобы существующие шаблоны не сломались. В редакторе нужны список доступных переменных, вставка по клику и preview с примерными данными.

Для первой версии достаточно глобального `streamer_display_name` в Settings. Пер-платформенные или пер-пресетные имена стоит вводить только при подтверждённом сценарии.

### Изображения и звуки

Не нужно создавать ещё одну несвязанную файловую систему. Существующий каталог `overlay-assets` уже находится рядом с `config.json` и `comm-relay.db`; его можно развить в локальную медиатеку:

- изображение элемента имеет приоритет над аватаром зрителя, а отсутствие изображения сохраняет avatar fallback;
- встроенные звуки остаются быстрым выбором, рядом появляется Custom file;
- база хранит только безопасный asset id/filename, не произвольный путь пользователя;
- загрузчик проверяет тип, размер и для звука длительность; overlay получает файл только через локальный HTTP route;
- удаление файла учитывает ссылки из команд, наград и будущей Reward Library;
- правила резервного копирования должны охватывать БД и каталог assets вместе.

Текущие `image_asset` и `sound_file` в таблицах — полезный задел, но их формат и жизненный цикл ещё не являются готовым контрактом.

## Предлагаемая последовательность обсуждения

Не стоит объединять все пункты в одну поставку. Предварительное разбиение:

1. **Admin interface follow-ups** — таблица Audience, все платформы, сортировка, открытие строки, selected states, таб-таксономия и выравнивание New stream. Tier 2, `spec-driven`.
2. **Live admin realtime stats** — подписка административных Leaderboard/Statistics на актуальные данные. Tier 2, `spec-driven`.
3. **Reward-linked message feedback** — новый message-aware grant/event contract, подсветка chat overlay, цитата и типы alert, политика очереди. Tier 2.5, `desktop-change`.
4. **Saved chat moments** — явное локальное сохранение выбранных сообщений. Tier 2.5, `desktop-change` из-за новой персистентной модели.
5. **Interactive media and templates** — streamer identity, расширенные переменные, локальная медиатека, изображения/звуки и варианты alert layout. Tier 3 или несколько связанных `desktop-change` после решения границ Reward Library.

## Вопросы, которые требуют решения

1. Убираем ли колонку Actions полностью после single-click открытия, или сохраняем явную кнопку как дополнительный affordance?
2. Нужен ли текст рядом со значками платформ в таблице, или достаточно доступного имени/tooltip?
3. Должна ли сортировка сохраняться между открытиями Audience?
4. Прозрачность общая для всех поверхностей, отдельная по поверхности или оба уровня с наследованием?
5. Может ли award обгонять ожидающие commands, если текущий видимый alert не прерывается?
6. Нужно ли хранить цитату награждённого сообщения после показа alert?
7. Где живут сохранённые сообщения: в Live, отдельной рабочей области или в будущей аналитике?
