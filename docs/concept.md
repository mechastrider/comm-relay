# Проект: CommRelay

## Цель проекта

CommRelay — локальное приложение на Go для объединения чатов стриминговых платформ и вывода сообщений в OBS через Browser Source.

Приложение развивается как отдельный продукт и не является частью mech-comm.

Главная цель стримового MVP — стабильно показывать сообщения из Twitch, YouTube и VK Live в одной OBS-встройке без облачного relay-сервиса и без зависимости от сторонних агрегаторов.

**Статус:** стримовый MVP **достигнут** (этапы 1–5). Реализованы зрители, лидерборд и механизм команд/наград (6a–6b). Канон реализованного поведения — `openspec/specs/`. Следующий горизонт — система признания вклада, прогресса и интерактивных наград: [`Interactive System v1`](interactive-system-v1.md) и [`roadmap.md`](roadmap.md).

# Что считать MVP

MVP ниже — исторический контракт того, что уже должно быть в продукте (и уже есть). Новые функции не расширяют этот список: они идут по roadmap.

В проекте было два уровня готовности:

1. **Первый прототип** — минимальная версия для проверки на стриме.
2. **Стримовый MVP** — версия, с которой можно регулярно проводить стримы на нужных платформах. **Достигнут.**

## Первый прототип

Цель: быстро проверить, что локальный сервер, WebSocket и OBS overlay работают как задумано.

Состав:

- Twitch connector
- минимальный HTTP-сервер
- WebSocket endpoint `/ws`
- OBS overlay `/overlay`
- базовая админка `/`
- единая модель сообщения
- простое сохранение настроек в `config.json`

Для прототипа достаточно Twitch. YouTube и VK Live не блокируют первую проверку, потому что основная техническая гипотеза — доставка сообщений в OBS в реальном времени.

## Стримовый MVP

Цель: рабочая версия для реальных стримов.

Платформы MVP:

- Twitch
- YouTube Live
- VK Live / VK Video

Функции MVP:

- одновременная работа нескольких платформ
- единый чат в OBS overlay
- админка для подключения и настройки платформ
- отображение статуса подключений
- настройка внешнего вида overlay
- устойчивый reconnect
- graceful shutdown
- сохранение настроек

# Архитектура

Приложение представляет собой локальный сервер.

Состав:

1. Коннекторы платформ
2. Внутренний агрегатор событий
3. HTTP-сервер
4. WebSocket-сервер
5. Веб-интерфейс управления
6. Overlay и дополнительные OBS-панели
7. `config.json` (настройки) и локальный SQLite (зрители/статистика, фаза 6a)

Схема:

```text
[Twitch]  \
[YouTube]  -> [CommRelay Core] -> [WebSocket /ws] -> [OBS Overlay /overlay]
[VK Live] /                                      -> [OBS Dock /dock/messages]
                                                 -> [OBS Leaderboard /overlay/leaderboard]
                                                 -> [OBS Alert /overlay/alert]
```

## HTTP-сервер

На первом этапе используется один локальный сервер и один порт:

- `http://localhost:17877/` — панель управления
- `http://localhost:17877/dock/messages` — журнал сообщений как Custom Browser Dock в интерфейсе OBS
- `http://localhost:17877/overlay` — OBS Browser Source (чат)
- `http://localhost:17877/overlay/leaderboard` — OBS Browser Source (лидерборд)
- `http://localhost:17877/overlay/alert` — OBS Browser Source (баннер команды)
- `ws://localhost:17877/ws` — WebSocket для overlay и панелей

Отдельные порты для админки и overlay не нужны в прототипе и MVP. Если позже появятся требования к изоляции, CORS или отдельному reverse proxy, это можно пересмотреть.

# Единая модель сообщения

Все платформы преобразуют сообщения к единому формату.

Пример структуры:

```go
type ChatMessage struct {
    ID          string
    Platform    string
    UserID      string
    Username    string
    DisplayName string
    Message     string
    AvatarURL   string
    Badges      []string
    Timestamp   time.Time
}
```

Overlay не должен знать ничего о Twitch, YouTube, VK Live или других платформах. Платформенные детали должны быть сведены к общим полям: `platform`, `display_name`, `avatar_url`, `badges`, `message`.

# Коннекторы платформ

## Twitch

Для первого прототипа использовать Twitch IRC.

Причины:

- быстрее реализовать
- не нужен OAuth для чтения публичного чата
- достаточно для проверки OBS overlay
- проще reconnect и отладка

Требования:

- получение сообщений чата
- автоматический reconnect
- поддержка одного канала в прототипе
- поддержка нескольких каналов позже
- обработка отключений

EventSub можно исследовать после прототипа, но не делать зависимостью первого запуска.

## YouTube Live

Два режима подключения:

### Simple (video URL) — режим по умолчанию

- пользователь указывает **channel handle** (`@name`) для автопоиска текущего эфира
- опционально: URL или ID конкретного live-видео (перекрывает автопоиск)
- OAuth не требуется
- чтение публичного live chat через InnerTube API (как веб-плеер)
- при отсутствии эфира connector ждёт и проверяет канал периодически
- риск: endpoint недокументирован и может измениться (аналогично VK Live)

### API (OAuth) — для авторизованного аккаунта

- OAuth-авторизация через **системный браузер** (кнопка Connect в админке)
- получение сообщений активного live-чата
- polling / gRPC stream с учётом лимитов API
- обработка ошибок квот
- сохранение токенов без логирования секретов

## VK Live / VK Video

Для стримового MVP connector использует **публичный read-only WebSocket API** платформы `live.vkvideo.ru` (ранее VK Play Live). Официальной документированной API для live chat у VK нет; решение основано на публичных endpoint'ах, которые использует веб-плеер (см. также community-проекты turnir-crystal, vklive-message-client).

Технический подход (MVP):

1. Получить анонимный WebSocket token из `<script id="app-config">` на `https://live.vkvideo.ru/`.
2. Разрешить slug канала через `GET https://api.live.vkvideo.ru/v1/blog/{slug}/public_video_stream/chat/user/` → `owner.id`.
3. Подключиться к `wss://pubsub.live.vkvideo.ru/connection/websocket?cf_protocol_version=v2` и подписаться на `channel-chat:{owner_id}`.
4. Парсить события `push.pub.data.type == "message"` в `ChatMessage`.

OAuth для MVP **не требуется** (только чтение чата). Отправка сообщений и приватные сценарии — вне scope.

Риски: endpoint'ы недокументированы и могут измениться; connector должен переживать ошибки и reconnect без падения процесса.

Требования:

- channel slug в config и админке
- получать сообщения текущего эфира (и офлайн-чата канала, если API отдаёт)
- обрабатывать reconnect и ошибки платформы
- показывать статус connector в админке

# Внутренний Event Bus

Все коннекторы публикуют события в общий канал.

Минимальное событие для прототипа и MVP:

- `ChatMessageReceived`

Пример:

```go
type Event struct {
    Type string
    Data any
}
```

Позже можно добавить:

- `UserJoined`
- `UserLeft`
- `StreamSessionStarted` / `StreamSessionEnded`
- `ViewerMerged`
- `CommandTriggered`
- `ConnectorStatusChanged`

Event bus должен иметь явно заданный bounded buffer. Поведение при переполнении нужно задокументировать в коде: например, отбрасывать самые старые сообщения для slow consumer, но не блокировать все коннекторы навсегда.

# WebSocket API

Назначение:

Передача сообщений в overlay в реальном времени.

Endpoint:

```text
GET /ws
```

Минимальный формат:

```json
{
  "type": "message",
  "platform": "twitch",
  "user": "Commander",
  "message": "Hello"
}
```

Расширенный формат:

```json
{
  "type": "message",
  "id": "twitch:123",
  "platform": "twitch",
  "username": "commander",
  "display_name": "Commander",
  "message": "Hello",
  "avatar_url": "https://example.com/avatar.png",
  "badges": ["broadcaster"],
  "timestamp": "2026-06-02T12:00:00Z"
}
```

После ручного удаления сервер отправляет всем клиентам событие:

```json
{
  "type": "message_deleted",
  "platform": "twitch",
  "id": "twitch:123"
}
```

Удаление из локальной истории выполняется action-запросом `POST /api/messages/delete` с `platform` и `id` в JSON-теле.

# OBS Overlay

Источник:

```text
Browser Source
```

URL:

[http://localhost:17877/overlay](http://localhost:17877/overlay)

Требования:

- прозрачный фон
- автоматическая прокрутка
- ограничение количества сообщений
- плавное появление
- настройка времени жизни сообщений
- темы отображения:
  - `default` — текущий вид с темной подложкой и цветовым акцентом платформы
  - `dashboard` — текст без фоновой рамки для зеленого фона, платформа выделяется цветной SVG-иконкой
- client-side reconnect к WebSocket
- аккуратное поведение при рестарте локального сервера

На первом прототипе дизайн может быть базовым. После добавления YouTube и VK Live нужно довести CSS до состояния, подходящего для реального стрима.

# Настройки

Хранение:

```text
config.json
```

Пример:

```json
{
  "server_port": 17877,
  "twitch": {
    "enabled": true,
    "channel": "example"
  },
  "youtube": {
    "enabled": false
  },
  "vk": {
    "enabled": false,
    "channel": "example"
  },
  "overlay": {
    "max_messages": 30,
    "message_ttl_seconds": 20,
    "font_size_px": 18,
    "display_mode": "normal",
    "theme": "default"
  },
  "admin": {
    "time_locale": "ru-RU"
  }
}
```

`admin.time_locale` задаёт язык интерфейса админки и OBS dock (русский / английский) и единую локаль времени; время выводится в 24-часовом формате.

`config.json` остаётся хранилищем настроек оператора и секретов. Зрители, склейки идентичностей и счётчики живут в локальном SQLite в том же каталоге. Полный архив чата в БД не требуется: в памяти по-прежнему кольцо последних сообщений для админки, dock и overlay.

Час сброса календарных суток лидерборда задаётся в настройках (по умолчанию 06:00 локального времени), а не полночь.

# Зрители, статистика и лидерборд

Этот продуктовый слой после MVP уже реализован как фундамент для [`Interactive System v1`](interactive-system-v1.md). Дальнейший порядок работ — в [`roadmap.md`](roadmap.md).

Каждое сообщение привязано к идентичности `(platform, user_id)`. Канонический **зритель** может объединять несколько идентичностей (разные платформы или несколько аккаунтов). Пока оператор никого не склеил, каждая идентичность — отдельный зритель.

Склейка — явное действие в админке (типично после стрима): поиск, карточка зрителя, «склеить с…». Счётчики складываются; лидерборд показывает одну строку. Автосклейка по совпадению ника не делается.

Два независимых счётчика:

- `message_count` — число сообщений;
- `xp` — очки опыта (XP). Начисляются за тихую activity-награду (интервал и лимит за стрим в настройках) и за ручные награды оператора; целевая модель развития позже отделит вклад за сессию, постоянный XP и расходуемые Credits (см. [`Interactive System v1`](interactive-system-v1.md)).

Лидерборд — отдельный прозрачный Browser Source `/overlay/leaderboard`, не смешивается с чатом. Три периода:

- **сессия** — кнопка «Новый стрим» в админке;
- **сутки** — календарный день оператора с настраиваемым часом сброса (по умолчанию 06:00 локального времени, не полночь), чтобы ночной эфир не резался в 00:00;
- **всё время**.

Сессия и сутки независимы.

# Команды чата и награды

Два каталога оператора в **Audience**: **Команды** (триггер `!…`, включено, кулдаун, картинка, надпись) и **Награды** (название, очки, текст баннера). В ядре нет обязательных `!jake` / `!nice`: при первом запуске есть удаляемые примеры `!gg`/`!hi` и награды Joke (+10) / Advice (+50); после удаления они не восстанавливаются при перезапуске.

Разбор команд — на **сервере**: целая строка `!команда` (без учёта регистра) ставит баннер в очередь `/overlay/alert` (аватар + надпись). Команды **не** меняют XP. Очки за поведение оператор выдаёт вручную через **Reward** в Live и dock; сообщения чата сами по себе XP не дают — только редкая тихая activity-награда по настройкам.

Успешные срабатывания команд и выдачи наград пишутся в журнал взаимодействий (для будущих достижений). Развитие этого фундамента в Contribution Rewards, достижения, Reward Library и rules engine описано в [`Interactive System v1`](interactive-system-v1.md).

# Требования к надежности

- автоматический reconnect для каждого connector
- graceful shutdown
- сохранение настроек
- устойчивость к падению одного connector
- отсутствие падения всего процесса из-за одной платформы
- понятные статусы подключения в админке
- защита от зависания из-за slow WebSocket client
- запрет на логирование токенов и секретов

# Логирование

Использовать `github.com/muonsoft/clog`.

Уровни:

- Debug
- Info
- Warn
- Error

Логи должны содержать:

- запуск и остановку сервера
- подключение платформ
- отключение платформ
- ошибки авторизации
- ошибки сети
- reconnect attempts
- статистику полученных сообщений

Секреты, OAuth-токены и приватные данные пользователей не логировать.
